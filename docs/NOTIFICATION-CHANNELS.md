# 通知链路（外置推送）

> 面向使用者的完整说明：为什么需要它、它怎么工作、怎么装、怎么排障。
> 协议与部署细节见 [`server/zcode-push/README.md`](../server/zcode-push/README.md)。

## 一、先理解一个硬约束

ZCode 的远程控制中继（relay）有一条**单控制端**规则：

> 同一台电脑，同一时间只允许**一个**手机终端接入。

这是官方行为，不是本 App 的限制。官方错误卡原文：

> 已被其他设备接管——另一台远程控制设备已经接入，同一时间只能保留一个手机控制端。

它带来一个绕不开的推论：**手机端只要多于一个"自己"在连，就必然互踢**。
而 App 里天然有不止一个：

| 终端 | 什么时候在跑 | 作用 |
|---|---|---|
| 会话页（WebView） | 你在 App 里看任务时 | 显示官方远程页面 |
| 后台监控 | 你离开 App 后 | 拉任务快照，判断完成/失败 |

两者交接稍有重叠，就会互相 KICKED，表现出来就是"**一直被其他设备接管**"。
v1.7.x 的一系列修复（让路退避、有序交接）把这个冲突压到了很低，但只要
还存在"多个终端争一个槽位"，问题就无法从根上消失。

## 二、外置通道：换一条完全不同的路

既然中继只允许一个终端，那就**不要再争那个槽位**——让桌面端主动把消息
推出来：

```
    ┌──────────────────────────────┐
    │  你的电脑（ZCode 桌面端）      │
    │                              │
    │  事件发生时执行 hook：         │
    │   • PermissionRequest 审批    │
    │   • Stop 任务结束             │
    └──────────────┬───────────────┘
                   │  HTTPS POST（带令牌）
                   ▼
    ┌──────────────────────────────┐
    │  zcode-push 服务              │
    │  （你自己的服务器，容器运行）   │
    │  • 鉴权 → 写 SQLite 队列      │
    │  • 投递确认后立即删除          │
    └──────────────┬───────────────┘
                   │  长轮询（25s 挂起）
                   ▼
    ┌──────────────────────────────┐
    │  手机 App                      │
    │  • 前台：UI 引擎轮询           │
    │  • 后台：头无引擎轮询          │
    │  • 共享游标 → 不会双响         │
    │  • 弹系统通知 + 进通知中心      │
    └──────────────────────────────┘
```

关键点：**整条链路没有一次触碰 relay 终端槽位**。所以它和会话页、后台
监控天然共存，不会造成任何接管冲突。

## 三、和内置 relay 通知的关系

两条通道**并行工作，互不替代**：

| | 内置 relay 通知 | 外置推送 |
|---|---|---|
| 消息来源 | 中继快照差分 | 桌面 hook 主动推 |
| 占用终端槽位 | **是** | 否 |
| 需要登录态 | 是 | 只认推送令牌 |
| 通知栏审批按钮 | 有 | 无（只深链到会话） |
| 依赖 | 中继可用、未被抢占 | 电脑上装好 hook |

两条都收到同一条事件时，会按 `(类型 + 会话 + 摘要)` 去重，不会响两次。

**为什么外置通道不加"允许/拒绝"按钮**：按钮需要把命令送回去，而能让
命令生效的通道（agent）本身就是一条 relay 终端——加回去等于把好不容易
绕开的槽位之争又请进来。所以外置通道只负责"告诉你"，操作点通知进
App 再做。

## 四、安装（三步）

### 步骤 1：服务器（只需一次，由你自己部署）

```bash
# 在服务器上
sudo mkdir -p /opt/zcode-push/data /etc/zcode-push
sudo openssl rand -base64 32 | sudo tee /etc/zcode-push/token >/dev/null
sudo chmod 600 /etc/zcode-push/token
sudo chown 10001:10001 /opt/zcode-push/data

# 拉取 server/zcode-push 目录到 /opt/zcode-push/src 后：
cd /opt/zcode-push/src && sudo docker compose up -d --build
```

再接一个 nginx location（完整片段见
[`server/zcode-push/README.md`](../server/zcode-push/README.md)）：

```nginx
location ^~ /zpush/ {
    proxy_pass http://127.0.0.1:8788;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_read_timeout 60s;
    proxy_buffering off;
    add_header Cache-Control "no-store" always;
}
```

验证：`curl https://<你的域名>/zpush/healthz` → `{"ok": true, "pending": 0}`

### 步骤 2：电脑上装 hook

```bash
bash server/zcode-push/install_zcode_hook.sh \
  --url https://<你的域名> \
  --token <上面 /etc/zcode-push/token 的内容>
```

脚本会做四件事：

1. 令牌写入 `~/.config/zcode-push/token`（权限 600）——**不放在命令行参数
   里**，避免进入 shell 历史与进程列表；
2. 生成上报脚本 `notify.sh`，**任何失败都静默退出 0**（通知发不出去绝不
   阻塞你的 ZCode 任务）；
3. 在 `~/.zcode/hooks/` 注册 `PermissionRequest` 与 `Stop` 两个 hook；
4. 立刻发一条自检消息，确认服务器接受。

想先看看会写什么：加 `--dry-run`。想撤掉：`--uninstall`。

如果已经在桌面端 设置 → 钩子 里手工配过，等价配置是：

| 事件 | 命令 |
|---|---|
| `PermissionRequest` | `~/.config/zcode-push/notify.sh PermissionRequest` |
| `Stop` | `~/.config/zcode-push/notify.sh Stop` |

### 步骤 3：手机 App 填配置

设置 → **外置通知通道** → 填同一个地址与令牌 → 点「保存并测试」。

- 地址必须是 `https://`（令牌走 header，明文不接受）；
- 令牌存在 Android 的加密存储里（与登录态同一级别），不进普通配置；
- 「保存并测试」会真的拉一次队列并回报结果，当场就能知道通不通。

## 五、排障：按这个顺序查

| 现象 | 先查这里 |
|---|---|
| 手机收不到，桌面端明明有审批 | 服务器 `curl https://<域名>/zpush/healthz` 看 `pending` 是否增长 |
| `pending` 一直是 0 | 桌面 hook 没触发：确认 hook 文件在 `~/.zcode/hooks/`，且桌面端设置里钩子处于启用状态 |
| `pending` 涨但手机不动 | App 里地址/令牌填错，或手机没网；点「保存并测试」重看提示 |
| 点测试提示 401 | 令牌不匹配：手机与服务器必须是同一个 `/etc/zcode-push/token` |
| 通知重复弹 | 两条通道都收到了；按 `(类型+会话+摘要)` 会去重，若仍重复请反馈 |
| 服务器重启后丢消息 | 队列在 SQLite（`/opt/zcode-push/data`），只要这个卷没删就还在；已投递的会立即删除，属正常 |

诊断信息在 设置 → 诊断 里；外置通道的消息也会进同一个通知历史。

## 六、安全边界

- **令牌**：只在两处存在——服务器的 `/etc/zcode-push/token`（600）和手机
  的加密存储。桌面端由 hook 从本地文件读取，不出现在命令行参数里。
- **传输**：只允许 `https://`；服务端所有数据接口都校验 `X-ZP-Token`，
  用常量时间比较，避免时序侧信道。
- **日志**：服务端只记方法与路径，**从不记录消息体或令牌**。
- **存储**：投递确认即删；未投递保留 7 天 / 最多 2000 条，磁盘不会无限增长。
- **权限**：容器以非 root（uid 10001）运行，`no-new-privileges`，只监听
  127.0.0.1，仅通过 nginx 对外。
- **可回滚**：`docker compose down` + 删掉 nginx 那段 `location` 即可完全
  移除，不影响任何现有服务。

## 七、常见问题

**Q：必须自己架服务器吗？**
是的。这条链路刻意不做公共中转——消息内容（任务标题、命令摘要）只经过
你自己的机器，这是隐私上的硬要求。服务器只用了 Python 标准库，一台最小
配置的云主机就够。

**Q：装了外置通道，还要不要保留内置 relay 监控？**
要。两者互补：外置通道依赖电脑上的 hook（电脑关机就没有），内置通道依赖
中继。任何一条活着就还有提醒。

**Q：会不会因为外置通道又多一条连接导致被接管？**
不会。外置通道是 App **主动发起的普通 HTTPS 请求**（长轮询），不是 relay
WebSocket，不占用控制端槽位，中继完全不知道它存在。

**Q：能不能也支持"允许/拒绝"按钮？**
技术上要再接回 relay 的 agent 通道，等于把槽位之争请回来。当前设计取舍是：
外置通道只做**通知**，点进 App 再操作。若后续官方开放了非终端式的命令
接口，再补按钮。
