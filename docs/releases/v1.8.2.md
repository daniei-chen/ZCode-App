## 新的检查更新链路

```
第 1 梯队  latest.json（主链路，不依赖 GitHub API）
           gh-proxy.com  →  jsDelivr  →  直连 raw  →  自有镜像
第 2 梯队  GitHub Release API（manifest 全挂时）
           gh-proxy.com →  ghproxy.net →  直连 api.github.com
第 3 梯队  发布页（github.com/releases/latest，最后兜底）
```

**为什么主链路改成 latest.json**：GitHub API 有匿名限流（60 次/小时/IP），
国内还常直接 403；而 raw 文件可以被 CDN 镜像，稳定得多，且 manifest 可以
直接携带 `sha256`。

## latest.json 契约

仓库根目录的 `latest.json` 由**发版脚本自动生成**（`build_release.sh`
第 4 步），因此不可能与 APK 漂移：

```json
{
  "version": "1.8.2",
  "tag": "v1.8.2",
  "apk": "ZCode-v1.8.2.apk",
  "sha256": "<64 hex>",
  "size": 30807781,
  "notes": "…首个 # 标题行…",
  "publishedAt": "2026-10-26T10:30:00Z"
}
```

## 安全：反代只能影响"能不能下到"，不能影响"下到的是什么"

这一点是引入公共反代的前提，三条约束同时成立：

1. **下载地址不采信 manifest**：APK URL 由本机内置的仓库地址与版本号拼装，
   manifest 里即便写了别的 URL 也不会被使用；
2. **强制 SHA-256 比对**：manifest 的 `sha256` 与实际下载文件逐字节比对，
   不符立即删除并报错（`缺少摘要 = 拒绝下载`，fail-closed）；
3. **安装器签名校验**：安装前再比对签名证书指纹（`07091ffd…`），证书不符
   的系统级拒绝。

因此即便某个公共反代返回了被替换的内容，也进不了安装流程。

## 下载也有反代链

`downloadProxyPrefixes = [gh-proxy.com, ghproxy.net, 直连]`。每次重试换一个
候选，但**每个候选的字节都过同一套 SHA-256 校验**。断点续传的 `.part`
文件跨候选复用（同一 URL 内容，代理只做转发）。
